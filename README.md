# 视频嗅探下载器（Chrome / Edge 浏览器扩展）

一个基于 Manifest V3 的浏览器扩展：**嗅探网页中的视频资源并下载到本地**。
支持 HLS（m3u8）、DASH（mpd）、MP4、WebM、FLV、TS 等常见格式；支持 AES-128 加密流解密、自动合并分片，并可在浏览器内把 TS 转封装为 MP4、把 WebM 双轨重建为一个文件；**对 B站、抖音、YouTube 这类把画面与声音拆成两条独立流的站点，下载时自动合并成一个含画面与声音的文件**。音视频分离一共覆盖 **7 种形态**（见[形态矩阵](#音视频分离的七种形态矩阵)），不是只修某一个站点。

> ⚠️ 免责声明：本扩展仅用于下载**您有权保存**的视频内容（如自己上传的视频、无版权限制的素材、已获授权的课程等）。
> 不支持也无法破解 DRM（Widevine）等版权保护加密内容。请遵守目标网站的条款和当地法律。

## 一、功能特性

| 能力 | 说明 |
| --- | --- |
| 网络层嗅探 | 监听所有网络请求，双通道识别：URL 后缀（`.m3u8`/`.mp4`/…）+ 响应 `Content-Type`（可捕获无后缀的动态流地址） |
| 内容签名识别 | URL 后缀与 `Content-Type` 都不可靠时（例如 m3u8 被以 `text/plain` 返回、地址完全不带后缀），拉取响应开头 4 KB 按**内容特征**判定真实类型（`#EXTM3U` / `<MPD` / `ftyp` / TS 同步字节 / EBML 等）；确认不是媒体的条目会被自动剔除，不污染列表 |
| 性能时间线回溯 | 打开扩展或点 `⟳` 重新扫描时，读取浏览器已记录的资源时间线（`PerformanceResourceTiming`），把**扩展开始观测之前**就已发出的媒体请求补报回来——覆盖 Service Worker 休眠、扩展后装/重载等漏检场景 |
| DOM 扫描 | 扫描页面 `<video>` / `<source>` 元素，捕获静态内联资源；识别 MSE/Blob 播放并给出提示 |
| HLS（m3u8）下载 | 解析 master/media 播放列表、多清晰度选择、并发下载分片、失败自动重试（3 次） |
| AES-128 解密 | 支持 `#EXT-X-KEY: METHOD=AES-128`（含自定义 IV / 序列号 IV），SAMPLE-AES/DRM 会明确提示不支持 |
| BYTERANGE | 支持 `#EXT-X-BYTERANGE`（含缺省偏移继承）与 `Range` 请求 |
| fMP4 支持 | 支持 `#EXT-X-MAP` 初始化分片（init + 分片直接合并即有效 MP4） |
| **角色识别（统一的判定链）** | 一条流到底是画面还是声音，按**可信度分层**判定：① URL query 显式声明（`&mime=audio%2Fmp4`、`?type=audio`…）→ ② YouTube itag 编号表 → ③ 路径/文件名角色词（`media-audio-und-mp4a`，需词边界与路径形态闸门，避免把 `/video/BV1xx` 播放页当成视频轨）→ ④ `Content-Type`。**判不出就返回"未知"，绝不瞎猜**——误判会把两条画面轨配成一对，比不配对更糟 |
| **音视频分离自动合并（7 种形态）** | 自动识别分离轨是**视频轨**还是**音频轨**（读文件头 `handler_type` / `stsd` 编解码器），把同一视频的两条轨按解码时间交织合成为一个文件。覆盖：B站 `.m4s` 整轨、抖音无后缀分离轨、YouTube 同路径 `&mime=` 声明轨、`&range=` 分片轨、HLS `#EXT-X-MEDIA` 独立音频组、DASH `.mpd` 清单里的音视频 Representation、WebM/Opus 轨。多视频页面按**请求时间邻近**配对（30 秒窗口内、一条音频不会被两个画面抢走），避免张冠李戴 |
| **DASH(.mpd) 清单解析** | 读透清单：`AdaptationSet` 的 `contentType` 直接给出谁是谁，`BaseURL` 逐级继承，`SegmentList` / `SegmentTemplate`(含 `SegmentTimeline`) / 单文件 `BaseURL` 四种分片形态都能展开成实际要下载的地址；`$RepresentationID$` / `$Number%05d$` / `$Time$` 模板变量按规范填充。清单里没有独立音频轨时如实说明 |
| **HLS 独立音频组** | 主流 HLS 把声音拆成一条独立 playlist（`#EXT-X-MEDIA:TYPE=AUDIO,URI="audio/index.m3u8"` + `#EXT-X-STREAM-INF:AUDIO="aac"`），画面 variant 本身不含声音。主动读主清单把音频组找出来补进列表，下载时把「画面 variant + 音频 playlist」一起取回、各自展开成一条完整轨再合并 |
| **WebM 双轨合并** | YouTube 的 VP9/Opus 轨是 WebM 而非 fMP4。按 EBML 结构解析：重建 Tracks（轨道号重编并同步改写所有块的轨道号）、统一时间基准、按 1 秒分桶重切簇再交织，并补上 `Duration`。容器由**内容**判定（不硬写 `.mp4`），WebM 产物落盘为 `.webm` |
| TS → MP4 | 内置 mux.js，在浏览器内把 TS 分片转封装为**可播放的 MP4**（失败自动回退为 .ts 输出） |
| **落盘前补索引（进度条能拖）** | 站点分发的 fMP4、HLS 的 `EXT-X-MAP` 分片、DASH 分片拼接、音视频合并——这几条路径产出的都是**碎片化 MP4**：能播，但进度条拖不动（`moov` 里没有帧索引，`mvhd.duration` 常是 `0xFFFFFFFF`）。落盘前统一重建为标准 MP4：提取全部 sample 的偏移/大小/时长/关键帧，重建 `stts/stss/ctts/stsc/stsz/stco`，写实 `mvhd/mdhd` 时长，输出「ftyp + moov + mdat」。**任何异常都原样落盘，绝不丢文件、绝不产出坏文件** |
| **时长以实测为准** | 清单里声明的时长经常是假的（站点写死值、单位搞错、直播流当成点播）。下载完成后从**已到手的分片**里逐块解析盒头量出真实时长，与声明值差得远时在任务说明里一并指出；界面只展示落在合理区间（1 秒 ~ 6 小时）内的声明时长，离谱的直接不显示 |
| 界面不堆积历史 | 下载任务区只显示**正在进行**的任务，做完即从界面消失，不再弹任何提示。记录仍写在会话存储里供测试与调试读取，只是不再占屏幕 |
| 防盗链处理 | 自动为源站域名注入 Referer / 移除 Origin（declarativeNetRequest 会话规则），解决常见 CDN 403；一条轨涉及多个 CDN 域名时逐个装规则 |
| 任务管理 | 实时进度（分片数 / 体积 / 速度）、随时取消、断点状态保存在会话存储 |
| 其他 | 直接下载普通视频文件、一键复制流地址（可配合 VLC 等播放器使用）、按类型筛选列表 |

## 二、安装方法

### 方式 A：加载解压后的文件夹（推荐，便于更新）

1. 打开 Chrome / Edge，地址栏输入 `chrome://extensions`（Edge 为 `edge://extensions`）；
2. 打开右上角的 **「开发者模式」**；
3. 点击 **「加载已解压的扩展程序」**，选择本目录（`video-sniffer` 文件夹）；
4. 工具栏出现紫色下载图标即安装成功（可在扩展菜单中「固定」到工具栏）。

> 安装时浏览器会提示"读取和更改您在所有网站上的数据"——这是嗅探所有网页视频所必需的权限。

### 方式 B：解压 zip 后按方式 A 加载

将 `store/dist/video-sniffer-1.0.1.zip` 解压到任意目录，然后按方式 A 加载。

### 在本地测试页上体验

打开 `test/test-page.html`（双击即可），按页面指引操作：
- 测试 1：HLS 流（出现在列表中的 `HLS` 类型，可"选择清晰度"下载）；
- 测试 2 / 3：普通 MP4 / WebM（点击「下载」直接保存）。

> 若以 `file://` 方式打开测试页，需要先在 `chrome://extensions` 的扩展详情页中打开「允许访问文件网址」。

### 本地手动验证（离线，推荐先做这一步）

上面的测试页依赖外网（mux.dev / MDN / jsdelivr），网络不通时会误判成"扩展坏了"。仓库里另有一套**完全离线**的验证环境：素材（m3u8 + 3 个真实 TS 分片 + MP4）直接从 `test/fixtures/` 托管到本地 HTTP 服务。

```bash
# 终端 1：启动本地验证服务（默认 http://127.0.0.1:8765/）
node test/serve_local.mjs
# 端口被占用时：node test/serve_local.mjs --port=8766

# 终端 2（可选）：先跑一遍自动自检，确认链路在你机器上可用
node test/verify_local_page.mjs
```

浏览器打开 `http://127.0.0.1:8765/`，页面上有逐步指引与"预期结果对照表"。核心验证点：

| 列表条目 | 类型标签 | 操作 | 预期结果 |
| --- | --- | --- | --- |
| `stream.m3u8` | HLS | 选择清晰度 → 直接下载 | 合并 3 个分片 → 转封装 → `.mp4`（约 838 KB，可播放） |
| `seg0/1/2.ts` | TS | — | 出现在「分片」分类中 |
| `flower.mp4` | MP4 | 下载 | 直接保存 `.mp4`（约 1.1 MB） |
| `movie-1-30080.m4s` | **M4S·视频** | **下载（含声音）** | **只产生 1 个 `.mp4`，既有画面也有声音** |
| `movie-1-30280.m4s` | **M4S·音频** | 单独下载 | 仅声音；已随上面那条自动合并，一般不需要 |
| `stream.mpd` | DASH | **选择清晰度** | 列出清单里的画面档位；下载时自动合并音频轨 → **1 个 `.mp4`** |
| `/dash2/stream.mpd` | DASH | **选择清晰度** | 画面 7 个分片 + 声音 8 个分片各自拼接后合并 → **1 个 `.mp4`** |

> 后三项是「测试 4 / 测试 5」，用的是从 B站 真实抓取的轨道样本，专门复现"音视频分离"这个场景——这也是验证本次修复是否在你机器上生效的最直接方式。测试 5 更进一步：把真实轨按 `moof` 边界切成 **init 段 + N 个分片**，还原成清单驱动的分片轨形态（真实 DASH 站点就是这样）。

## 三、使用方法

1. **正常播放**目标网页上的视频（或让页面加载视频列表）；
2. 点击工具栏中的扩展图标，弹出的面板会列出嗅探到的资源；
3. 按需操作：
   - `HLS` 类型 → 点击 **「选择清晰度」** → 选择清晰度/直接下载 → 在「下载任务」区查看进度；若主清单声明了独立音频组，面板会提示「声音在独立音频轨上」，下载时自动合并；
   - `DASH(.mpd)` → 点击 **「选择清晰度」**：面板直接列出清单里的画面档位（分辨率 / 编码 / 码率 / 分片数，按分辨率降序）；清单里还有独立音频轨时，下载会自动把两串分片各自拼接后合并，并明确告知；
   - `MP4/WEBM/FLV...` → 点击 **「下载」**（由浏览器原生下载，支持大文件）；
   - **「复制」** → 复制流地址，可用于 VLC / PotPlayer / ffmpeg 等工具；
   - `M4S·视频` / `视频轨`（按钮为 **「下载（含声音）」**）→ 该站把画面与声音拆成了两条独立流（B站、抖音、YouTube 等站点都是这样），点击后自动下载两条轨并合成**一个**文件；若你只要画面，可点旁边的「仅视频」；
   - `M4S·音频` / `音频轨` → 这条声音已被上面的视频轨自动合并，一般无需单独下载（纯音频流则可直接下载；DASH 的音频轨是一串分片，点「单独下载」会自动拼接成一条完整音频）；
   - `BLOB` 条目 → 说明视频经 MSE 播放，下载对应的网络列表中的流地址即可。
4. 右上角按钮：`⟳` 重新扫描页面、`🗑` 清空列表、`⚙` 设置（保存目录 / 输出格式 / 并发数）。

### 输出说明

| 源格式 | 默认输出 | 说明 |
| --- | --- | --- |
| TS 分片（最常见） | `.mp4` | 浏览器内转封装；若个别流不兼容则自动回退输出 `.ts`（播放器均可播放） |
| fMP4 分片（`m4s`） | `.mp4` | init 分片 + 媒体分片直接合并 |
| 音视频分离双轨（`m4s` / 抖音式无后缀 / DASH 清单轨 / HLS 独立音频组） | **单个 `.mp4`** | 两条轨在本地按解码时间交织成一个文件（含画面与声音）；合并失败会保底保存视频轨、并把音频轨另存为 `.audio.m4a`（两份都在，不丢数据），任务说明中写清原因 |
| 音视频分离双轨（WebM / Vorbis·Opus） | **单个 `.webm`** | 同上，但容器按**内容**判定 —— 不会被硬写成 `.mp4`，否则播放器会用错解码器 |
| AES-128 加密流 | 同左 | 下载过程中自动解密 |
| 直播流 | `.ts`/`.mp4` | 只能保存开始下载时刻已缓存的片段（会弹窗提示） |

## 四、工作原理（架构）

```
┌─────────────┐     消息      ┌──────────────────┐     webRequest     ┌──────────┐
│   popup     │ ◄───────────► │  background      │ ◄───────────────── │ 目标网页  │
│ （界面/任务）│               │ （Service Worker）│   嗅探 m3u8/mpd/ts │          │
│  读清单发现   │               │ 角色判定 + 分片归一│                    └──────────┘
│  独立音频轨   │               └───────┬──────────┘
└──────┬──────┘                       │ 创建/转发
       │ 启动下载（单文件 / 一串分片 / 清单） ▼
┌──────────────────────────────────────────────────────────┐
│  offscreen 文档（下载引擎）                                 │
│  解析 m3u8 / 展开清单与分片 → 并发下载 → AES-128 解密          │
│  → 按容器选择合并器：fmp4merge（MP4）/ webmmerge（WebM）      │
│  → mux.js 转 MP4 → 保存到本地（容器按内容判定，不硬写后缀）      │
└──────────────────────────────────────────────────────────┘
```

- **background（Service Worker）**：`webRequest` 嗅探（MV3 可用观测模式）、按标签页维护结果（`storage.session`）、转发消息、注入防盗链规则（一条轨跨多个 CDN 域名时逐个装）、抓取 `m4s`/WebM 文件头判定轨道类型、**对判定不出类型的响应做内容签名识别**、**按 URL 声明的角色定性并摘掉 `&range=` 分片参数**；
- **content script**：扫描 DOM 中的视频元素，并**回溯浏览器资源时间线**补报早先发生的请求；
- **offscreen 文档**：MV3 中 Service Worker 无 DOM/Blob 能力，下载引擎运行在此（分片下载、Web Crypto 解密、Blob 合并、mux.js 转封装、fMP4/WebM 双轨合并）；
- **popup**：资源列表、清晰度选择（HLS 与 DASH 各一套面板）、任务进度、设置、音视频轨配对提示、**主动读清单发现独立音频轨**。

### 音视频分离的七种形态矩阵

音视频分离不是某一个站点的问题，而是**一类问题**。修完 B站 与抖音后，据此把同类形态一次性排查穷尽：

| # | 形态 | 真实站点举例 | 识别依据 | 处理方式 |
| --- | --- | --- | --- | --- |
| ① | **无后缀分离轨，两条 CT 都是 `video/mp4`** | 抖音（`media-video-avc1` + `media-audio-und-mp4a`） | 路径角色词（`media-audio-*`）+ 文件头 `hdlr`/`stsd` | 读文件头定角色；路径完全不同时按**请求时间邻近**配对 |
| ② | **URL query 显式声明角色** | YouTube（`/videoplayback?…&mime=audio%2Fmp4`） | `mime` / `type` 等 query 参数（含 `%2F` 与双重编码） | 声明优先于 CT；CT 不可信时直接定性，省掉一次内容探测 |
| ③ | **一条轨被 `&range=0-999999` 切成 N 条** | YouTube | URL 中 `range` / `rn` / `rbuf` 等分片参数 | 入库前摘掉分片参数归一成一条，体积取 `clen`；否则下载只有前 1MB |
| ④ | **HLS 独立音频组** | 主流 HLS（`#EXT-X-MEDIA:TYPE=AUDIO` + `#EXT-X-STREAM-INF:AUDIO="aac"`） | 主清单的 `#EXT-X-MEDIA` | 主动读主清单发现音频 playlist 并补进列表；下载时画面 variant 与音频 playlist 一起取回、各自展开成完整轨再合并 |
| ⑤ | **DASH 清单里的音/视频 Representation** | `.mpd` 站点（此前清单一个字都没读） | `AdaptationSet` 的 `contentType` / `mimeType`（**不用猜**） | 解析清单抽出音/视 Representation 及其 init 段与全部分片；「选择清晰度」列出画面档位，下载时两串分片各自拼接后合并 |
| ⑥ | **音频轨是 WebM/Opus 而非 fMP4** | YouTube（VP9/Opus） | EBML 魔数 → WebM 轨解析 | 新增 WebM 合并器：重建 Tracks、重编轨道号并同步改写块、统一时间基准、按 1 秒分桶重切簇交织、补 `Duration`；容器按内容判定，WebM 就落 `.webm` |
| ⑦ | **一个页面有多对轨** | 多视频列表页 / 连续播放 | 分组键 + 请求时间 | 同组内取质量最高的一对；跨组兜底改为**时间邻近配对**（30 秒窗口、一条音频不会被两个画面抢走），超窗坚决不配——宁可提示"未发现配套音频轨"，也不要拿别的视频的声音去凑 |

配套的两处**误判防护**（比"判不出"更值得防的是"判错"）：
- **路径判定加形态闸门**：只有「目录形态」（末尾是 `/`）或「文件形态」（末段带扩展名）才允许按路径判角色 —— 否则 B站 播放页 `/video/BV1xx411c7mD` 会被当成一条视频轨。
- **判不出就返回未知**：宁可显示"未识别"，也不给一个猜测的角色；误判会把两条画面轨配成一对，比不配对更糟。

回归覆盖：`mediarole`(52) + `mpd`(96) + `webmmerge`(27) + `e2e_dash_parts`(23) + `e2e_youtube_style`(21) + `popup_tracks`(67)。

#### 顺带修掉的一个隐蔽 bug：AES-128 解密会静默吃掉分片末尾

写 `e2e_hls_aes` 时实测发现：`crypto.subtle.decrypt` 在 **Chrome 与 Node 里都会自动去掉 PKCS#7 填充**（实测「明文 32 B → 密文 48 B → 解密回 32 B」），而原代码又无条件自己去一次填充 —— **每个分片都可能被多吃 1~16 字节**。它只在「明文末尾恰好落在 1~16」时暴露（分片是二进制，约 6%），所以此前一直表现为偶发、且很难归因。

修法是不猜环境：**解密输出比输入短就说明环境已去过填充，不再动手**；真要自己动手时校验「最后 `pad` 个字节全部等于 `pad`」。`test/e2e_hls_aes.mjs` 用 `node:crypto` 独立解密算出参照产物，与扩展产物**逐字节比对**；`test/engine.test.mjs` 另加两组确定性回归（末尾字节枚举 0x00~0xff 与多种非 16 倍数长度）。

### 形态①：B站 的 `.m4s` 整轨（最早修复的两个形态之一）

**现象（用户实测反馈）**：在 B站 点下载后得到两个文件——一个有画面没声音，一个有声音没画面。

**原因**：B站 采用 DASH 架构，画面与声音分别存在两条独立流里（页面用 MSE 把两条轨合成播放）：
- 视频轨：如 `62131_da3-1-30080.m4s`，`moov` 里的 `hdlr` 为 `vide`，`stsd` 为 `avc1`；
- 音频轨：如 `62131_da3-1-30280.m4s`，`hdlr` 为 `soun`，`stsd` 为 `mp4a`。

两者都是完整的 fMP4 文件，单独下载任何一个都只有一半内容。

**实现**（`lib/fmp4merge.js`）：
1. **识别**：后台用 `Range: bytes=0-65535` 只取前 64 KB 文件头，解析 `moov` 判定这是视频轨还是音频轨（含分辨率 / 声道 / 采样率 / 编解码器）；
2. **配对**：按「路径目录 + 主文件名末段数字替换为 `*`」分组（先摘扩展名再取数字，避免 `.m4s` 里的 "4" 干扰），同一组内各取质量最高的一条视频轨与音频轨配对；
3. **合并**：以视频轨的 `ftyp` 为基准**重建 `moov`**（新建 `mvhd` + 视频 `trak` + 音频 `trak` + 含两条 `trex` 的 `mvex`），重编号音频轨的 `track_ID`（1↔2）并同步改写 `tkhd` / `trex` / 每个 `traf.tfhd`，再按 `tfdt` 解码时间把两轨的 `moof+mdat` 片段交织输出成**单个 MP4**；
4. **兜底**：任何一步失败都不会让下载白费——保底保存视频轨，并把音频轨另存为 `.audio.m4a`（两份文件都在，可自行用工具合并），任务说明里写清原因。

**验证**（`test/fmp4merge.test.mjs`、`test/e2e_merge.mjs`）：用从 B站 真实抓取的轨道样本（`test/fixtures/dash/`）跑通全链路，并用 Chrome 实际打开产物确认 `videoWidth > 0` **且** `webkitAudioDecodedByteCount > 0`（画面和声音都真的被解码了），最终只产生 1 个文件。

### 形态①：抖音的无后缀分离轨（最早修复的两个形态之一）

**现象（用户实测反馈）**：在抖音下载的视频没有声音。

**实抓验证**（`test/douyin_probe.mjs`，2026-10-15 用视频详情页实测）：抖音网页版同样把画面与声音拆成两条独立流，但形态与 B站 完全不同：

| 项 | 抖音 | B站 |
| --- | --- | --- |
| 视频轨 URL | `.../media-video-avc1/?a=6383&…`（**无后缀**） | `...xxx-1-30080.m4s` |
| 音频轨 URL | `.../media-audio-und-mp4a/?a=6383&…`（**无后缀**） | `...xxx-1-30280.m4s` |
| Content-Type | **两条都是 `video/mp4`** | 均为 `video/mp4` |
| 路径结构 | 两条**完全不同**（`media-video-*` vs `media-audio-*`，且带不同签名目录） | 同目录、文件名仅数字段不同 |
| 容器 | fMP4 分片（`ftyp`+`moov(mvex)`+`sidx`+`moof/mdat` 序列），`avc1` + `mp4a` | fMP4 分片，`avc1/17` + `mp4a` |

这暴露了三个叠加的缺陷，导致下载的视频必然无声：
1. 无后缀的两条轨被判成普通条目（音频轨在较早版本里更是因为只处理 `video/*` 而被完全忽略）；
2. 音视频配对池只收 `.m4s`（fmp4）类型条目，无后缀分离轨不参与配对；
3. 即使参与，两条轨的 URL 路径结构完全不同，按路径分组**永远配不上对**。

**实现（本次修复）**：
1. **捕获**：`onHeadersReceived` 增加 `audio/*` 分支（新增 `audio` 类型，含 `.m4a/.mp3` 等后缀与独立音频文件）；`type=media` 的请求即使 CT 不可信也记为候选；
2. **类型保真**：`normalizeKind` 不再让「CT 推测的后缀」把 `video`/`audio` 通用类型反向升级成 `mp4`（否则无后缀轨会因落到常见类型而不被探测）；
3. **探测**：轨道探测范围从 `fmp4` 扩展到 `fmp4 + video + audio + 无后缀的 mp4`，识别出各自的角色（视频轨/音频轨/完整文件）；
4. **配对**：保留按路径分组（B站 场景），新增**跨组 1v1 兜底**——页面上只有一条视频轨 + 一条音频轨时直接配对（多视频页面不启用，避免张冠李戴）；
5. **界面**：新增 `视频轨`/`音频轨` 标签与 `AUDIO` 徽章，配对成功时显示「下载（含声音）」；完整文件显示「画面与声音都在这个文件里」。

**验证**：`test/e2e_douyin_style.mjs`（本地复现抖音形态的端到端：嗅探 → 识别 → 配对 → 合并落盘双轨 MP4，15/15）+ `test/douyin_real_sample.test.mjs`（**用实抓的 512 KB 真实轨头部字节**：`avc1 782×576` + `mp4a 2ch/44.1kHz` → 合并 → Chrome 实际播放确认画面与声音都被解码，12/12）。真实样本存放在 `test/fixtures/dash/douyin_*.m4s`。

## 七、常见问题

**Q：为什么某些视频点了下载后提示加密无法下载？**
A：该视频使用了 SAMPLE-AES / DRM（Widevine）等版权保护，此类内容设计上就无法被第三方下载，扩展会明确提示。

**Q：下载报 HTTP 403？**
A：部分 CDN 有防盗链。扩展已自动注入 Referer 规则；若仍失败，多为源站校验了登录态或特殊令牌，可尝试在**已登录状态下、于目标页面上**再触发一次。

**Q：为什么有的页面「不播放」也能看到视频，有的必须播放？**
A：取决于**站点什么时候去请求视频流**，而不是扩展。多数站点为了省流量，要等你点播放才去请求清单和分片；但不少站点会自动播放或预加载首段，这些资源不播放也会出现。极少数工具能"提前"看到，是因为它们往页面里注入了脚本、去读页面 JS 内存里的地址——代价是要改动目标页面的运行环境。本扩展走的是"不侵入页面"的路线，用三条互补通道把能看到的都拿到：
① 实时监听网络请求；② 打开扩展/点 `⟳` 时**回溯浏览器资源时间线**，补报扩展开始观测之前就已发生的请求（Service Worker 休眠、扩展后装等场景）；③ 对 URL 与响应头都判不出类型的地址，**拉前 4 KB 按内容特征定性**（所以"不带后缀、还以 `text/plain` 返回的 m3u8"也能被认出来；体积 ≥ 256 KB 的类型不明响应同样会进候选，兜住"URL 一串签名参数 + `application/octet-stream`"这种最麻烦的形态）。

两个诚实说明的限制：页面**从未请求过**的地址谁都拿不到；响应头带 `Cache-Control: no-store` 的资源不会进入浏览器资源时间线（实测 Chrome 155），这类只能靠实时监听那条通道。

**Q：直播能下载吗？**
A：直播流只能下载"点击下载那一刻"已缓存的部分（相当于一段录像快照），会弹窗确认。

**Q：为什么 B站（或其他 DASH 站点）下载下来会分成"画面"和"声音"两个文件？**
A：这是这类站点的架构决定的：画面与声音是两条独立的流（`vide` 轨 + `soun` 轨），页面用 MSE 在播放时把它们合成。本扩展会自动识别并配对，下载时直接合成**一个**含画面与声音的 MP4——列表里视频轨的按钮显示为「下载（含声音）」就表示已配对成功；音频轨那条无需单独下载。若列表里只有一条轨，通常是另一条还没被页面加载，播放几秒后再点 `⟳` 重新扫描即可。

**Q：下载下来的 MP4 能播放，但进度条拖不动 / 拖了没反应？**
A：这是**碎片化 MP4（fMP4）**的典型症状，不是文件损坏。这类文件的 `moov` 里只有轨道描述，逐帧索引散在成百上千个 `moof` 里，很多源的 `mvhd.duration` 还写成 `0xFFFFFFFF`（"未知时长"）。浏览器内核（Chrome/Edge）偶尔能靠 `sidx` 或扫描整个文件兜住，所以"能播"；但系统播放器、剪映、PotPlayer 之类常常直接不给拖，文件一大浏览器也会卡很久。

扩展从 v1.0.1 起会在**落盘前自动重建索引**：把散在 `moof` 里的逐帧信息提取出来，重建为标准 MP4 的 `stts/stss/ctts/stsc/stsz/stco` 表，输出「ftyp + moov + mdat」这种任何播放器都能精确定位的结构，同时把 `mvhd/mdhd` 的时长写实。任务说明里出现「已重建索引（N 轨 / M 帧 / X 秒）」就表示这一步生效了。

重建有三条保命规则：只处理内容确实是 MP4 的、任何异常都原样落盘（绝不丢文件）、绝不产出半成品（尺寸或偏移对不上就中止）。

**Q：任务显示"已完成"但文件在哪？**
A：在浏览器默认下载目录中；HLS 合并输出的文件因浏览器对扩展下载的限制会保持在下载目录根下，无法进入自定义子目录（设置中的"保存目录"对普通文件下载生效）。

**Q：列表里每条后面那个 "9:53:38" 是视频时长吗？为什么一直不变？**
A：**不是时长**，那是这条资源被嗅探到的时间。早期版本把「请求发生的时间戳」直接格式成了 `HH:MM:SS` 摆在条目副标题里，又没有任何标签，很容易被当成视频时长；而条目的时间戳是固定的，不刷新界面它就永远停在那儿。

从 v1.0.2 起改成相对时间（"3 分钟前" / "2 小时前"），精确钟点只在鼠标悬停时的提示里出现。视频的真实时长看任务说明里的「实测时长」——那是从**下载到手的分片**里逐块量出来的，不是清单里声明的值（清单声明的时长经常是假的）。

**Q：下载完的任务为什么自己从界面上消失了？**
A：v1.0.2 起任务区只显示**正在进行**的任务，完成或失败即从界面移除、不再弹提示，也不堆积历史记录。记录本身仍写在会话存储里（测试与调试要读），只是不占屏幕。

**Q：为什么某个站点扫不到视频 / 只下到声音？**
A：先点页面里的视频播放几秒，再点右上角 `⟳` 重新扫描——多数站点要等播放才去请求流地址。若还是没有，点页脚「**复制诊断信息**」，把复制到的文本直接贴回来：里面包含当前页面嗅探到的全部条目（类型 / 来源 / 体积 / 识别结果 / 完整地址）与清单解析情况，据此就能定位是"没请求过"、"URL 与响应头都判不出类型"还是"清单结构没覆盖到"。

**Q：下载下来只有声音、没有画面？**
A：从 v1.0.3 起这种情况会被明确处理，不会再静默发生：
- **转封装前先看 TS 里的视频编码**。自动转 MP4 只支持 H.264；遇到 HEVC(H.265)、MPEG-2 等编码时，硬转会让视频轨悄悄消失（只剩声音），因为转封装器认不出这些编码的参数集。现在会**直接落原始 TS**，任务说明里写清楚"检测到 HEVC(H.265) 视频，自动转 MP4 只支持 H.264"——用支持该编码的播放器（VLC / PotPlayer / MX Player 等）就能直接播。
- **转完之后再自检一次**：产物里确实没有视频轨时，同样回退为原始 TS 并说明，绝不交付一个"只有声音的 MP4"。
- 如果任务说明里没有这类提示、文件却只有声音，那更可能是**源本身就只有声音**（纯音频流），列表里该条的徽章会显示「音频」。

**Q：下载到一半失败，提示"分片 N/M 下载失败：Failed to fetch"？**
A：这是**链路层被掐断**（实测该形态下 Chrome 记录的是 `net::ERR_CONNECTION_CLOSED`：CDN 或代理在传输中途重置连接），不是地址失效——同样的地址重试往往就能过。v1.0.3 起把分片重试从 3 次加到 5 次、退避从线性改为按平方增长（最长 2.4 秒），并且**连续失败会自动降速**，不再往一条已经不稳的链路上猛灌请求。若仍然失败，可在设置里把并发数调低（如 2～3）再试。

**Q：大文件安全吗？**
A：HLS 合并需要把分片暂存在内存中，数百 MB 通常无压力；下载超大数据（>2GB）建议改用复制地址 + ffmpeg/yt-dlp 等桌面工具。

**Q：支持 Firefox 吗？**
A：当前构建面向 Chrome / Edge（Chromium 内核，MV3）。Firefox 的 MV3 对 `webRequest`、offscreen 等支持存在差异，需要另行适配。

## 八、技术要点备忘

- MV3 中 Service Worker 无法 `URL.createObjectURL`，Blob 相关操作必须借助 offscreen 文档；
- 经实测：跨上下文通过 `downloads.download(blobUrl)` 保存时，Chromium 会忽略自定义文件名（用 UUID 命名）；本扩展采用「offscreen 内锚点下载 + 后台下载确认」方案保证文件名正确；
- m3u8 解析为顺序状态机，正确支持 `EXTINF` 与 `EXT-X-BYTERANGE`/`EXT-X-KEY` 交错出现（这是常见的兼容性坑）；
- **fMP4 双轨合并**无需重新编码：两条轨各自带 `timescale`，`tfdt` 是各自时基下的解码时间，因此交织时不必换算时间，只要保证 `track_ID` 全局唯一、`mvex` 里为每条轨各有一个 `trex`（缺了 `trex` 播放器会拒绝解析）；
- 轨道的 `track_ID` 改写必须**同时**覆盖 `tkhd`、`trex` 与**每个** `traf` 的 `tfhd`——只改前两者会让分片指向错误的轨，表现为"能解析但没声音"；
- **实测（Chrome 155）：响应头带 `Cache-Control: no-store` 的资源不会进入 `PerformanceResourceTiming` 时间线**，因此性能时间线回溯对这类资源无效（A/B 对照实验记录见 `test/e2e_sniff_gaps.mjs` 的注释）。真实流媒体一般用 `public, max-age=…`，不受影响；
- **fMP4 转标准 MP4 的三个坑**（都在 `lib/mp4index.js` 里踩过，测试可复现）：① `sample_flags` 的 `sample_depends_on == 2` 表示「不依赖其他帧」= **是关键帧**，当成非关键帧会让整张 `stss` 颠倒，播放器从 P 帧开始解码直接报 `Failed to send video packet`；② chunk 偏移不能按「减去前面 moof 总大小」估算——真实文件里 `mdat` 前常夹着 `sidx`（B站每段近 5KB）和 `free` 填充，漏减就是整体错位；③ 源文件的 `edts/elst` 记的是源分片时间轴（`media_time` 常与 `ctts` 的正偏移配套），重建后必须丢掉并把 `ctts` 归一到首帧 PTS = 0，否则 35 秒的文件会被读成 0.734 秒；
- 判不出类型时不要急着丢弃，也不要不加验证地全收：先记为「候选」，再用**内容签名**验证（`#EXTM3U` / `<MPD` / `ftyp` / `0x47` 同步字节），验证失败的直接删除——这样既补上了漏检，又不会让列表被噪音淹没。
